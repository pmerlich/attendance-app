- **שני ממצאים חדשים בחומרה גבוהה (HIGH)**, שניהם אמיתיים אך אף אחד מהם אינו פרצת אבטחה ניתנת לניצול: מלכודת נגישות מקלדת בשני פקדי טופס חובה (**P2-01**), ופער בשלמות נתונים/חוויית משתמש שבו עריכות אופליין המתנגשות עם שינוי מקביל בשרת נמחקות בשקט במקום להיות מוצגות למשתמש כפי שמתועד (**P2-02**). השני משמעותי יותר לפריסה עם כמה מכשירים/עובדים.
- **כמה ממצאים בחומרה בינונית (MEDIUM)** מתרכזים סביב מוכנות תפעולית ולא נכונות: כמעט ואין רישום לוגים בצד השרת (**P2-07**), נתיב שליחת מייל האיפוס החדש יורש את אותה נקודה עיוורת (**P2-08**), הגיבויים אוטומטיים אך שחזור מעולם לא נבדק (**P2-06**), מדיניות הפרטיות עדיין כוללת placeholder במקום ערוץ יצירת קשר אמיתי (**P2-09**, ידוע כבר מ-`M-02` בביקורת הקודמת), ומערך הבדיקות היחיד הוא הצמדת נסיגה על טקסט מקור/HTML ולא בדיקות אינטגרציה אמיתיות מול אימות/הרשאות/סנכרון (**P2-05**).
- **כל הממצאים הקריטיים/גבוהים מהביקורת הקודמת (`C-01`, `H-01`, `H-02`) עדיין מתוקנים** בקוד הנוכחי, כפי שאומת בקריאה חוזרת של הקבצים הרלוונטיים והרצה חוזרת של מערך הבדיקות (11/11 עוברות) לצד `typecheck`/`lint`/`build`.
- **התכונה החדשה של המפגש הזה (איפוס סיסמה במייל) עברה ביקורת עצמית** כחלק מהסבב הזה: לא נמצאו ממצאים קריטיים/גבוהים; הערת ערוץ תזמון (timing) אחת בחומרה נמוכה (**P2-13**) והערת ניקוי אחת בחומרה נמוכה (**P2-14**).

## B. מחסנית הפרויקט שזוהתה (מאומתת מראיות במאגר)

- **Framework:** `vinext` (מסגרת תואמת Next.js עם React Server Components) 1.0.0-beta.2, React 19.2.6, `@vitejs/plugin-rsc`.
- **סביבת ריצה/אחסון:** Cloudflare Workers (`wrangler` 4.92.0, `@cloudflare/vite-plugin`), אין `wrangler.toml`/`.json` בשליטת גרסאות — התצורה חיה ב-`localBindingConfig` בתוך `vite.config.ts` ומתגבשת ל-`dist/server/wrangler.json` בזמן build.
- **מסד נתונים:** Cloudflare D1 (SQLite), הסכמה מוגדרת עם Drizzle ORM (`drizzle-orm` 0.45.2, `db/schema.ts`) לצורכי טיפוסים וכתיבת migrations, אך הטבלאות בפועל נוצרות/משתנות דרך שמירות `CREATE TABLE IF NOT EXISTS`/`ALTER TABLE ... ADD COLUMN` אידמפוטנטיות בתוך `app/auth-core.ts`/`app/api/*/route.ts` — דפוס סכמה מרפאת-עצמה ולא migrate-then-deploy קלאסי.
- **אחסון קבצים:** Cloudflare R2 (binding בשם `FILES`), אובייקטים פרטיים (תמונות פרופיל, קבלות/קבצים מצורפים).
- **עיצוב:** כלי Tailwind CSS v4 קיימים כ-devDependency אך הממשק בפועל (`app/globals.css`, כ-1,220+ שורות אחרי המפגש הזה) הוא CSS כתוב ידנית עם custom properties, לא מחלקות Tailwind — אומת שאין שימוש במחלקות Tailwind ב-`app/page.tsx`.
- **אימות:** פנימי, מבוסס session-cookie (`app/auth-core.ts`), hashing סיסמאות PBKDF2-SHA-256 (100,000 סבבים — התקרה הקשיחה של `crypto.subtle` ב-Workers), טוקני session מגובבים ב-SHA-256, cookies עם `HttpOnly`/`SameSite=Lax`/`Secure` (ב-HTTPS), תפוגה מתגלגלת ל-365 יום.
- **אופליין:** מסד IndexedDB מותאם (`app/offline-store.ts`), Service Worker כתוב ידנית (`public/sw.js`, מטמון מעטפת network-first, ללא מטמון ל-API), `BroadcastChannel` לסנכרון בין לשוניות של אותה זהות.
- **מייל (חדש במפגש זה):** Resend (`https://api.resend.com`) דרך `fetch` רגיל, ללא תלות SDK נוספת (`app/email.ts`).
- **בדיקות:** `node:test` (מובנה), קובץ אחד (`tests/rendered-html.test.mjs`), מופעל דרך `npm test` = build + הרצה.
- **CI:** GitHub Actions — `.github/workflows/ci.yml` (typecheck+lint+build+test על push/PR) ו-`.github/workflows/backup.yml` (ייצוא D1 מתוזמן).
- **תלויות:** 3 תלויות runtime (`drizzle-orm`, `react`, `react-dom`), 24 תלויות dev; הצמדת גרסאות כמעט מדויקת לחלוטין; lockfile בשליטת גרסאות.

## E. ממצאים חדשים (סבב זה)

### P2-01 — גבוה — נגישות מקלדת — בוררי סוג חיוב ומצב חשבון אינם נגישים במקלדת

**קטגוריה:** נגישות / נגישות מקלדת
**סוג:** פגם מאומת
**מיקום:** `app/globals.css:353` (`.billing-options input { display: none; }`), `app/globals.css:631` (`.account-mode-options label input { display: none; }`); שימוש ב-`app/page.tsx:4025` (`<fieldset className="account-mode-options">`) וב-`app/page.tsx:4534` (`<fieldset className="billing-options">`).

**ראיה:** אלמנטי `<input type="radio">` האמיתיים שמאחורי שני הבוררים המעוצבים מוסתרים עם `display: none`, מה שמסיר אותם הן מעץ הנגישות והן מסדר ה-Tab (בשונה מדפוסי `visibility:hidden` הניתנים למיקוד). אלמנטי ה-`<label>` העוטפים אינם כוללים `tabIndex` או `onKeyDown` שמפצים על כך. לעומת זאת, `.worker-checkbox` (תיבות סימון שיוך עובדים) משתמש בעיצוב `accent-color` ונשאר ניתן להפעלה במקלדת — המלכודת ספציפית לשני הפקדים המעוצבים כ-radio.

**הבעיה:** משתמש מקלדת-בלבד, משתמש במכשיר-מתג, או משתמש קורא-מסך אינו יכול לבחור מצב חשבון (עובד מול מעסיק, מוצג בהרשמה/הגדרות פרופיל) או סוג חיוב פרויקט (גלובלי/שעתי/משולב, שדה חובה בכל יצירה/עריכה של פרויקט) כלל.

**מדוע זה חשוב:** אלה שדות חובה בשניים מהטפסים המרכזיים ביותר באפליקציה (הגדרת חשבון ויצירת/עריכת פרויקט). כשל WCAG 2.1.1 (מקלדת) בפקד חובה שאין דרך לעקוף הוא חסימה מוחלטת עבור המשתמשים הנפגעים, לא חוויה פחותה.

**תיקון מומלץ:** להחליף את `display: none` בדפוס "מוסתר-חזותית אך ניתן-למיקוד" (`position:absolute; width:1px; height:1px; overflow:hidden; clip:rect(0,0,0,0); white-space:nowrap;`) כך שה-input המקורי יישאר בסדר ה-Tab ויגיב למקשי חיצים/Space כפי שקבוצת radio עושה באופן טבעי, ולהוסיף מסגרת `:focus-visible` נראית ל-`<label>`/פקד המותאם עבור משתמשי מקלדת רואים. אין צורך בשינויי JavaScript — זו יכולת מובנית של `<input type="radio">` שה-CSS הנוכחי מדכא באופן פעיל.

**סיכון תאימות:** נמוך. החלפת טכניקת CSS בלבד על פקדים מעוצבים כבר קיימים; המראה החזותי למשתמשי עכבר/מגע נשאר זהה אם דפוס ההסתרה החזותית מיושם נכון (יש לוודא שלא מופיע ריבוע פיקסל בודד).

### P2-02 — גבוה — סנכרון אופליין — פעולות בתור שנדחו/התנגשו נמחקות בשקט, בניגוד להתנהגות המתועדת

**קטגוריה:** שלמות נתונים / פתרון התנגשויות / התנהגות אופליין
**סוג:** פגם מאומת
**מיקום:** `app/page.tsx:1084-1099` (`syncQueuedOperations`), בממשק מול תשובות `409` של `versionConflict()` ב-`app/api/state/route.ts` (מנגנון `expectedUpdatedAt`).

**ראיה:**
```
if (response.status >= 500 || response.status === 408 || response.status === 425 || response.status === 429) {
  interrupted = true; setSyncState("error"); break;
}
// Retrying an unchanged 4xx payload cannot succeed. Remove legacy invalid data
// instead of presenting it forever as a connectivity/sync failure.
await removeQueuedOperation(operation.id);
setSyncError("");
rejected += 1;
```
ענף זה רץ עבור **כל** תשובת 4xx שאינה {408,425,429,5xx}, כולל התנגשות `409` — גוף התשובה של השרת (הנושא הודעת שגיאה בעברית ואובייקט `conflict.server` מובנה) לעולם אינו נקרא (`response.json()` אינו נקרא בנתיב זה). `lastError` — השדה שממנו ניזונים גם ממשק "הסרת פעולות שנדחו" וגם `retryQueuedOperations()`/`discardRejectedOperations()` — לעולם אינו נקבע עבור פעולות רגילות (רק עבור קבצים מצורפים שנדחו, ב-`app/page.tsx:1149`). חיפוש `.conflict` ב-`app/page.tsx` מחזיר אפס אזכורים — מטען ההתנגשות שהשרת כבר מחשב לעולם אינו נצרך על ידי הלקוח, לא במצב מקוון ולא באופליין.

**הבעיה:** אם משתמש עורך רשומה באופליין (למשל דיווח שעות, תשלום, או פרויקט), ומישהו אחר משנה את אותה רשומה לפני שהמכשיר חוזר להתחבר, הפעולה הממתינה נמחקת ללא הודעה, ללא באנר, וללא דרך לראות מה נוסה או מדוע נכשל — השינוי של המשתמש פשוט נעלם. זה סותר ישירות את ההתנהגות המתועדת ב-`docs/SOLO_WORKER_AUDIT.md` (S-05: "הדחייה נשמרת על הפעולה עם סיבת השרת... המשתמש יכול לנסות שוב או להסיר פעולות שנדחו"; S-29: "השינוי נשמר בתור עם הסבר ופעולות retry/הסרה").

**מדוע זה חשוב:** זהו אובדן נתונים שקט בדיוק בתרחיש — עריכה אופליין המתנגשת עם שינוי מקביל בצד השרת — שמנגנון `expectedUpdatedAt`/409 קיים כדי להגן מפניו. החצי בצד השרת של זיהוי ההתנגשות תקין (אומת: `expectedUpdatedAt` נשלח בכל סוג עריכה והשרת מחזיר 409 מובנה); הטיפול בצד הלקוח בתשובה הזו הוא שמשמיט את המידע במקום לפעול לפיו.

**תיקון מומלץ:** בעת תשובת 4xx שאינה ניתנת לניסיון חוזר במהלך replay, לקרוא את `response.json()`, לקבוע את `operation.lastError` להודעת השרת במקום למחוק את הפעולה לגמרי (כך שממשק "הסרת פעולות שנדחו"/ניסיון חוזר הקיים יוכל למצוא אותה), ולהציג הודעה נראית (בשימוש חוזר בדפוס `NoticeToast`/פופאובר פרטי הסנכרון הקיים כבר במקומות אחרים) במקום לנקות בשקט את `syncError`. מקרי 4xx שהם באמת קבועים (למשל רשומה שנמחקה בצד השרת, ישות שאינה קיימת עוד) עדיין עשויים להצדיק הסרה אוטומטית, אך צריכים לומר זאת למשתמש במקום להיעלם ללא הסבר.

**סיכון תאימות:** נמוך-בינוני. נוגע בנתיב הטיפול בשגיאות של לולאת replay הסנכרון; דורש בדיקה שמוודאת (א) שפעולה מתנגשת נשארת כעת נראית וניתנת לפעולה, ו-(ב) שנתוני תור פגומים/מיושנים באמת אינם נערמים לנצח ללא דרך לנקות אותם (הפעולה הקיימת "הסרת פעולות שנדחו" כבר מספקת מוצא כזה ברגע ש-`lastError` נקבע נכון).

**אימות לאחר תיקון:** בדיקת אינטגרציה שמכניסה פעולה לתור, משנה את אותה רשומה דרך "session" שני, מאפשרת ל-replay של התור לרוץ, ומוודאת שהפעולה נשארת בתור עם `lastError` לא ריק ונראית בממשק; אימות ידני עם שתי לשוניות/מכשירים העורכים את אותו דיווח זמן.

### P2-15 — נמוך — עוגיית ה-session אינה משתמשת בקידומת `__Host-`

**קטגוריה:** אימות / ניהול session
**סוג:** המלצה
**מיקום:** `app/auth-core.ts` — `SESSION_COOKIE = "menahel_session"`, נבנית ב-`sessionCookie()` כ-`${SESSION_COOKIE}=...; Path=/; HttpOnly; SameSite=Lax; Max-Age=...` (בתוספת `Secure` ב-HTTPS).

**הבעיה:** העוגייה כבר לעולם אינה מגדירה attribute של `Domain` (כך שהיא כבר host-only כברירת מחדל לפי RFC 6265 - הפער המעשי קטן ממה שהוא נראה), מגדירה `Path=/`, ומגדירה `Secure` ב-HTTPS — כלומר היא כבר מקיימת את כל מה ש-`__Host-` דורש חוץ מהשם עצמו. שינוי שמה ל-`__Host-menahel_session` יגרום לדפדפן **לאכוף** את התכונות האלה (Secure, ללא Domain, Path=/) במקום להסתמך על כך שהשרת תמיד יגדיר אותן נכון, בעלות כמעט אפסית.

**מדוע זה חשוב:** חומרה מעשית נמוכה בהתחשב בכך שהאפליקציה כבר host-only בפועל, אך זהו צעד חיזוק ידוע וחינמי שמסיר כל סיכון עתידי שהוספה בטעות של `Domain=` תרחיב בשקט את היקף העוגייה.

**תיקון מומלץ:** לשנות את שם העוגייה ל-`__Host-menahel_session` ב-`SESSION_COOKIE`, ב-`sessionCookie()`, וב-`clearSessionCookie()`; לשמור חלון מעבר קצר שבו השרת גם מקבל (אך כבר לא מגדיר) את שם העוגייה הישן כך שמשתמשים שכבר מחוברים לא ינותקו בכפייה עם הפריסה, או לקבל התחברות חוזרת חד-פעמית כחלק מהשינוי.

**סיכון תאימות:** נמוך-בינוני אם לא מטופל בזהירות — שינוי שם נאיבי ינתק את כל המשתמשים המחוברים כרגע בו-זמנית עם הפריסה. יש לתכנן את המעבר (למשל לקבל את שני השמות בקריאה במהלך תקופת מעבר) או להזהיר את המשתמש במפורש שהפריסה הזו תדרוש מכולם להתחבר מחדש.

**אימות לאחר תיקון:** לוודא שהדפדפן דוחה את העוגייה אם `Secure`/`Path=/`/היעדר-`Domain` יופרו אי-פעם בטעות (זו הנקודה של הקידומת - היא הופכת לחוזה שהדפדפן אוכף), ושתהליכי כניסה/יציאה/חידוש session עדיין עובדים מקצה לקצה.

### P2-16 — נמוך — חסרות כותרות תשובה `Cross-Origin-Opener-Policy` ו-`Cross-Origin-Resource-Policy`

**קטגוריה:** אבטחה / כותרות HTTP
**סוג:** המלצה
**מיקום:** `secureResponse()` ב-`worker/index.ts` (שורות ~30-52) — מגדיר `x-content-type-options`, `x-frame-options`, `referrer-policy`, `permissions-policy`, `content-security-policy` (ש-`frame-ancestors 'none'` שלו כבר מחליף את `x-frame-options`), ו-`strict-transport-security` ב-HTTPS, אך לא `Cross-Origin-Opener-Policy` או `Cross-Origin-Resource-Policy`.

**הבעיה:** אף אחת מהכותרות אינה מוגדרת כרגע על אף תשובה.

**מדוע זה חשוב:** `Cross-Origin-Opener-Policy: same-origin` מבודד את הקשר הגלישה של האפליקציה מחלונות/popups חוצי-מקור שהיא פותחת או שפותחים אותה (הגנה נוספת מפני התקפות מסוג תזמון חוצה-חלונות/Spectre); `Cross-Origin-Resource-Policy: same-site` חוסם ממקורות אחרים להטמיע את תשובות האפליקציה הזו (תמונות, JSON) בדפים משלהם. לא צפויה השפעה תפקודית מאף אחת מהן על האפליקציה הזו (היא עצמה אינה מטמיעה משאבים חוצי-מקור, וגם אין תועלת לגיטימית לכך שאתרים אחרים יטמיעו אותה), כך שזהו כמעט חיזוק חינמי.

**תיקון מומלץ:** להוסיף `headers.set("cross-origin-opener-policy", "same-origin")` ו-`headers.set("cross-origin-resource-policy", "same-site")` לצד כותרות האבטחה האחרות ב-`secureResponse()`.

**סיכון תאימות:** נמוך. כדאי לוודא שנתיב אופטימיזציית התמונה `/_vinext/image` וזרימת הקישור החיצוני ל-Waze/Google Maps (שפותחת לשונית חדשה דרך `target="_blank"`, לא `window.open()`, כך ש-COOP לא אמור להשפיע עליה) ממשיכים לעבוד כמצופה לאחר הוספת COOP, מכיוון ש-COOP יכול לעיתים להשפיע על זרימות מבוססות `window.open()` אם קיימות כאלה.

**אימות לאחר תיקון:** לוודא ששתי הכותרות מופיעות בתשובות (`curl -I`), ולאמת ידנית שנתיב אופטימיזציית התמונה וכל אינטראקציית פתיחת-חלון (ניווט מפה) עדיין עובדים.

1. **גבוה — P2-01** (בוררים לא נגישים במקלדת): תיקון CSS בלבד, סיכון נמוך, השפעת משתמש גבוהה; לבצע ראשון.
2. **גבוה — P2-02** (אובדן נתונים שקט בהתנגשות אופליין): הממצא הפתוח המשמעותי ביותר; דורש זהירות בנתיב שגיאות replay הסנכרון בתוספת בדיקה חדשה.
3. **בינוני — P2-07 ואז P2-08**: להוסיף רישום לוגים מינימלי בצד השרת קודם (P2-07), מה שסוגר גם את חצי הנראות של החשש ב-P2-08.
4. **בינוני — P2-05**: להוסיף תשתית בדיקת אינטגרציה עם שני חשבונות; מחזק באופן טבעי את הביטחון בתיקון P2-02 ברגע ששניהם נחתים.
5. **בינוני — P2-06**: לכתוב ולבדוק סקריפט שחזור מול מסד D1 של staging.
6. **בינוני — P2-04**: תיקוני ניגודיות, סיכון נמוך.
7. **בינוני — P2-03**: תיקון תיעוד בלבד, ללא סיכון, ניתן לביצוע בכל עת.
8. **בינוני — P2-09**: פעולת מפעיל (לא Claude) — לספק יצירת קשר פרטיות אמיתית.
9. **נמוך — P2-10, P2-11, P2-12, P2-13, P2-14, P2-16**: לקבץ יחד כליטוש בסיכון נמוך לאחר סיום הפריטים הנ"ל (P2-16 היא תוספת של שתי שורות כותרות).
10. **נמוך — P2-15** (קידומת עוגיית `__Host-`): לבצע בנפרד ובמכוון — בשונה מהאחרים באצווה הזו, היא תנתק בכפייה כל משתמש מחובר כרגע עם הפריסה אלא אם מיושמת תקופת מעבר; יש לתזמן ולתקשר זאת ולא לשלב אותה בשקט באצווית ליטוש.

כל קבוצה צריכה לעקוב אחרי "הגדרת סיום" (Definition of Done) של הפרויקט עצמו: `npm run typecheck && npm run lint && npm test`, סקירת `git diff`, והפעלה ידנית של הזרימה הנוגעת בדבר לפני שמסמנים אותה כפתורה.

## J. פעולת מפעיל נדרשת — הגדרת שליחת מייל איפוס סיסמה (לא פגם, אלא שלב פריסה)

תכונת איפוס הסיסמה שנוספה במפגש זה מיושמת ונבדקת במלואה (typecheck/lint/build/tests כולם עוברים) אך **לא תשלח מייל בפועל עד שהמפעיל ישלים הגדרה חד-פעמית זו**, מכיוון ששום ספק מייל לא יכול למסור באופן לגיטימי לתיבות דואר צד-שלישי שרירותיות מדומיין לא מאומת — זו דרישת אנטי-ספאם משותפת לכל ספק, לא מגבלה ספציפית ליישום הזה:

1. להוסיף את הדומיין שלך ל-Resend (https://resend.com, מסלול חינמי: 100 מיילים ליום / 3,000 בחודש) ולאמת אותו על ידי הוספת רשומות ה-DNS SPF/DKIM ש-Resend מספק — זה יכול להיות אותו דומיין שאתה מתכנן לחבר ל-Cloudflare עבור האפליקציה עצמה, או תת-דומיין שלו (למשל `mail.yourdomain.com`).
2. ליצור מפתח API של Resend.
3. להגדיר אותו ב-Worker הפרוס כסוד (לעולם לא לבצע לו commit): `wrangler secret put RESEND_API_KEY --name menahel-avoda`, ואז להדביק את המפתח כשמתבקש.
4. להגדיר את כתובת השולח באותו אופן: `wrangler secret put RESEND_FROM_EMAIL --name menahel-avoda` (למשל `מנהל עבודה <no-reply@yourdomain.com>`) — חייבת להיות כתובת על הדומיין המאומת.
5. לפיתוח מקומי, ליצור קובץ `.dev.vars` (כבר ב-gitignore) בשורש המאגר עם `RESEND_API_KEY=...` ו-`RESEND_FROM_EMAIL=...` אם ברצונך לבדוק שליחות מייל אמיתיות מקומית; בלעדיו, `npm run dev` ירשום את קישור האיפוס למסוף במקום לשלוח מייל, וזה מספיק כדי להפעיל את הזרימה מקצה לקצה.
6. לאחר ההגדרה, לשלוח לעצמך מייל בדיקת איפוס אמיתי אחד כבדיקה סופית (לפי המלצת P2-08) במקום להסתמך על לוגים בלבד.

אין צורך בשינויי קוד עבור כל זה — זו הגדרת חשבון/DNS/סוד לחלוטין על חשבונות Cloudflare הקיימים שלך וחשבון Resend החדש, וזה חינמי בהתחשב בנפח הצפוי של האפליקציה הזו.
