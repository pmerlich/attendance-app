# דוח ביקורת מלא: מנהל עבודה

תאריך ביקורת: 2026-09-03
היקף: `app/`, `db/`, `worker/`, `public/`, `tests/`, קבצי תצורה ותיעוד תפעולי.

## תקציר מנהלים

המערכת היא MVP מתקדם של אפליקציית ניהול עבודה עם פרויקטים, לקוחות, עובדים, טיימרים, דיווחי זמן, תשלומים, הוצאות, קבצים, דוחות, PWA ושמירה אופליין.

הקוד עובר כרגע `npm run lint` ו-`npm test`, אבל הבדיקות הקיימות כמעט אינן בודקות מסד נתונים אמיתי, הרשאות, משתמשים מקבילים, סנכרון או כשלי רשת. לכן מצב הבדיקות אינו מוכיח שהמערכת מוכנה לנתוני לקוחות אמיתיים.

## ממצאים לפי חומרה

### קריטי: אין הגנה מפורשת על כותרות זהות ב-API

**מיקום:** `app/api/state/route.ts`, `resolveIdentity()`.

השרת בונה את זהות המשתמש ישירות מהכותרות `oai-authenticated-user-id` ו-`oai-authenticated-user-email`. אם ה-Worker נגיש ישירות או אם שכבת proxy מאפשרת ללקוח להעביר את הכותרות האלה, לקוח יכול לבחור `userId` וליצור או לקרוא סביבת עסק אחרת. גם `businessId` נגזר מהכותרת בלבד.

**תיקון מומלץ:** לוודא שהנתיב נגיש רק דרך שכבת האימות שמזריקה את הכותרות, למחוק כותרות זהות שמגיעות מהלקוח לפני העברה פנימה, ולהוסיף בדיקת אינטגרציה שמוכיחה שבקשה חיצונית עם כותרות מזויפות מקבלת `401`.

### גבוה: IndexedDB משותף לכל החשבונות באותו דפדפן

**מיקום:** `app/offline-store.ts`, `DATABASE_NAME`.

השם הקבוע `menahel-avoda-offline` אינו כולל משתמש, עסק או סביבה. משתמש שמתנתק ומתחבר לחשבון אחר באותו דפדפן עלול לראות cache ישן ולשלוח queue של החשבון הקודם תחת הזהות החדשה. זה עלול לגרום להצגת מידע שגוי ואף לשינוי רשומה עם מזהה שקיים בשני עסקים.

**תיקון מומלץ:** להשתמש במסד נפרד לכל `businessId`/`userId`, או להוסיף namespace לכל רשומה ולנקות/להחליף אותו עם שינוי זהות. אין לסנכרן פעולות מתור שנוצר עבור זהות אחרת.

### גבוה: אין מנגנון conflict resolution אמיתי לסנכרון אופליין

**מיקום:** `app/page.tsx`, `syncQueuedOperations()` ו-`applyOptimisticOperation()`.

פעולות נשמרות לפי `operationId`, אבל אין versioning, compare-and-set או בדיקת `updated_at` לפני עדכון. אם אותו פרויקט נערך בשני מכשירים, הפעולה האחרונה יכולה לדרוס שינוי חדש יותר. במקרה של `409` התור נעצר, אך אין מסך שמציג איזו פעולה נכשלה או איך לפתור אותה.

**תיקון מומלץ:** להוסיף `updatedAt/version` לכל ישות, לשלוח את הגרסה שהלקוח קרא, להחזיר conflict מובנה, ולהציג למשתמש אפשרות לבחור server/local.

### גבוה: פעולות CRUD אינן אטומיות עם audit log

**מיקום:** `app/api/state/route.ts`, ברוב פעולות הכתיבה.

לעיתים שינוי הנתונים מתבצע בפקודה אחת ו-`appendAudit()` מתבצע לאחריה בפקודה נפרדת. אם כתיבת audit נכשלת, הנתון השתנה אך אין תיעוד. בפעולות פרויקט יש גם עדכון, מחיקת שיוכים והוספת שיוכים במספר פעולות נפרדות.

**תיקון מומלץ:** להשתמש ב-`db.batch()` לכל שינוי הנתונים ולרשומת audit המתאימה, או במנגנון transaction אמיתי. להוסיף בדיקה שמדמה כשל באמצע.

### גבוה: סל המחזור אינו שחזור מלא

**מיקום:** `app/api/state/route.ts`, `restoreClient`, `restoreProject`, `restoreEmployee`.

מחיקה שומרת רק רשומת soft-delete חלקית. שחזור פרויקט מחזיר את הפרויקט והלקוח, אבל לא משחזר בהכרח `project_workers`, שיוכי עובדים, מצב קודם, או קשרים שנמחקו. מחיקת עובד אינה מסירה אותו מ-`project_workers`, ושחזור עובד מחזיר אותו בלי שחזור metadata היסטורי.

**תיקון מומלץ:** לשמור snapshot מלא או לבצע soft-delete בלבד לכל הישויות הקשורות, ולהוסיף בדיקות שחזור עבור לקוח עם פרויקטים, פרויקט עם עובדים ועובד משויך.

### גבוה: מחיקת פרויקט משאירה קבצים ב-R2

**מיקום:** `app/api/state/route.ts`, `deleteProject` ו-`deleteClient`.

המחיקה מעבירה פרויקט או לקוח ל-soft-delete, אך לא מסמנת attachments כמחוקים ולא מוחקת אובייקטים מ-R2. בהמשך, גם שחזור אינו משחזר ניהול קבצים כי הקבצים נשארו מחוץ למחזור החיים של הרשומה.

**תיקון מומלץ:** להגדיר מדיניות מפורשת: soft-delete שומר קובץ נגיש מסל המחזור, ו-purge סופי מוחק גם את רשומת attachment וגם את אובייקט R2. להוסיף job לניקוי orphan objects.

### גבוה: יצירת schema בזמן כל בקשת API

**מיקום:** `app/api/state/route.ts`, `prepareRequest()` ו-`ensureCoreSchema()`.

כל בקשת GET/POST מפעילה `CREATE TABLE IF NOT EXISTS`, `PRAGMA table_info`, יצירת אינדקסים ו-`PRAGMA optimize`. זה מוסיף latency, עומס ועלות, ומערבב migration עם request path.

**תיקון מומלץ:** להריץ migrations בפריסה בלבד. אם חייבים fallback זמני, להשתמש בדגל תהליך עם טיפול בכשל, אך לא להסתמך עליו כמנגנון migration של production.

### בינוני: אינדקסים חסרים או לא מותאמים לכל השאילתות

**מיקום:** `app/api/state/route.ts`, `ensureCoreSchema()`.

יש אינדקסים שימושיים, אך חסרים אינדקסים מורכבים למסלולים החמים, למשל `projects(business_id, deleted_at)`, `clients(business_id, deleted_at)`, `audit_log(business_id, created_at)`, ו-`time_entries(project_id, deleted_at, ended_at)`. הבעיה תורגש כשהנתונים יגדלו.

**תיקון מומלץ:** להריץ `EXPLAIN QUERY PLAN` על דוחות, dashboard ו-project activity, ואז להוסיף רק אינדקסים שמוכיחים שיפור.

### בינוני: אימות תאריכים חלש

**מיקום:** `app/api/state/route.ts`, `addManualTime`, `updateTimeEntry`, `addPayment`, `addExpense`.

השרת בודק פורמט `YYYY-MM-DD`, אך לא בודק שהתאריך אמיתי או שאינו עתידי. ערכים כמו `2026-02-31` עלולים לעבור, ותאריכים עתידיים מעוותים דוחות.

**תיקון מומלץ:** parser אמיתי לתאריך, מדיניות ברורה לגבי תאריך עתידי, ובדיקת `max` בטפסים כעזר UX בלבד. האימות חייב להישאר בשרת.

### בינוני: אין מגבלת אורך/כמות מספקת לכל payload עסקי

**מיקום:** `app/api/state/route.ts`, `POST`.

יש מגבלת body כללית, אך מערכים כמו `workers` מאפשרים עד 100 פריטים, ופרטי JSON אינם עוברים schema מלא. חלק מהערכים עוברים `String()` ומקבלים default במקום להידחות, מה שמסתיר שגיאות לקוח.

**תיקון מומלץ:** schema validation מרכזי לכל action, עם שגיאות עקביות. לדחות ערכים חסרים או לא חוקיים במקום להמיר אותם בשקט.

### בינוני: stopTimer עוצר כל טיימר פעיל של המשתמש בעסק

**מיקום:** `app/api/state/route.ts`, `stopTimer`.

הפעולה אינה משתמשת ב-id של הטיימר אלא מעדכנת כל `time_entries` פעיל של המשתמש. בדרך כלל זו כוונת המוצר, אך במקרה של נתונים כפולים/תקלה היא יכולה לסגור יותר מטיימר אחד, וה-audit מציין רק `ownerId` ולא את הרשומות שנסגרו.

**תיקון מומלץ:** לשלוח `timerId`, לעדכן רשומה אחת בלבד, ולהחזיר שגיאה אם אין טיימר מתאים.

### בינוני: חישוב כסף באמצעות `real` ומספרי JavaScript

**מיקום:** `db/schema.ts`, `app/page.tsx`, `app/api/state/route.ts`.

סכומים נשמרים כ-floating point (`real`) ומחושבים ב-JavaScript. סכומים עשרוניים עלולים לצבור שגיאות עיגול, ובחלק מהמסכים המטבע מוצג תמיד כ-€ למרות שלעסק יש שדה currency.

**תיקון מומלץ:** לשמור סכומים ביחידות הקטנות ביותר כמספר שלם, או להשתמש ב-decimal עקבי. להעביר currency כחלק מה-state ולהשתמש ב-`Intl.NumberFormat` לפי המטבע העסקי.

### בינוני: דוחות מוגבלים ללא pagination או export server-side

**מיקום:** `loadState()` ו-`loadProjectActivity()`.

דיווחי זמן, תשלומים, הוצאות, קבצים ו-audit מוגבלים ל-50/100/1000 רשומות. אין pagination, cursor או סימון שהנתונים חלקיים. דוח גדול עלול להיות איטי או לא שלם.

**תיקון מומלץ:** pagination לפי cursor, סינון תאריכים בצד השרת, וייצוא שמבוסס על query מלא ומבוקר.

### בינוני: Service Worker שומר HTML ו-assets ללא ניהול גרסה robust

**מיקום:** `public/sw.js`.

ה-service worker משתמש בשם cache ידני `v3`, ומטמון ניווטים נוספים בזמן ריצה. משתמש יכול לקבל HTML ישן שמפנה ל-assets שאינם תואמים לאחר deployment. אין טיפול בגרסת cache שנכשלה באמצע התקנה.

**תיקון מומלץ:** להשתמש ב-build hash או בגרסת deployment, לבצע precache אטומי, ולוודא שהחלפת worker אינה משאירה shell מעורבב.

### בינוני: CSP מאפשר `unsafe-inline`

**מיקום:** `worker/index.ts`, `secureResponse()`.

`script-src 'self' 'unsafe-inline'` ו-`style-src 'self' 'unsafe-inline'` מקטינים את ההגנה מפני XSS. ייתכן שזה נדרש ל-framework, אבל צריך לצמצם זאת אם אפשר.

**תיקון מומלץ:** לבדוק nonce/hash-based CSP, לפחות להסיר `unsafe-inline` מסקריפטים אם ה-build מאפשר זאת, ולהוסיף בדיקת headers אוטומטית.

### נמוך: דליפת מידע וסיכון פרטיות במצב אורח

**מיקום:** `resolveIdentity()` ו-`loadState()`.

סביבת האורח משותפת לכל המבקרים, וכל הפעולות מותרות בפועל. ההודעה מזהירה שהנתונים ציבוריים, אך משתמש יכול לשנות או למחוק נתוני הדגמה של משתמשים אחרים.

**תיקון מומלץ:** להפוך את האורח לקריאה בלבד, או לאפס את סביבת ההדגמה ולבודד session באמצעות seed זמני.

## בעיות UX והתנהגות שכדאי לשפר

1. אין מסך ברור לפעולה שנדחתה מהתור. המשתמש רואה שגיאת סנכרון כללית בלי action, סיבה או אפשרות תיקון.
2. לאחר דחיית פעולה שאינה `409`, הפעולה נמחקת מהתור. זה מונע retry אך עלול לגרום לאובדן פעולה בלי היסטוריה מקומית.
3. יצירת לקוח חדש מתוך טופס פרויקט היא שתי פעולות נפרדות. אם הלקוח נוצר והפרויקט נכשל, נשאר לקוח ריק.
4. בחירת לקוח בפרויקט נעשית לפי שם (`clientName`) ולא לפי id. שמות כפולים או שינוי שם עלולים לבחור לקוח לא נכון.
5. מחיקת לקוח ומחיקת פרויקט מבוססות על התאמות לפי שם באופטימיזציה המקומית, לא רק לפי id. שני לקוחות עם אותו שם עלולים לקבל state שגוי בדפדפן.
6. התצוגה והטפסים מציגים מטבע יורו גם כאשר סכמת העסק מאפשרת מטבע אחר.
7. מצב loading ראשוני אינו מוצג באופן מלא בזמן שה-cache והשרת נטענים, ולכן משתמש עלול לראות נתוני demo לפני שהנתונים האמיתיים הגיעו.

## פערי בדיקות

הבדיקות הנוכחיות מאשרות SSR, מבנה HTML, נוכחות מחרוזות, headers מסוימים, build, וקיום קוד מסוים. חסרות בדיקות עבור:

- הרשאות manager/employee לכל action.
- בידוד בין שני עסקים ושני משתמשים.
- זיוף כותרות זהות.
- accept invitation, expiration, reuse וחשבון שכבר מחובר.
- סנכרון offline עם כשלי רשת, retry, 401, 409 ו-5xx.
- race conditions בהפעלת שני טיימרים או שתי פעולות זהות.
- rollback כאשר כתיבת audit או R2 נכשלת.
- שחזור מלא מסל המחזור.
- העלאת קובץ עם MIME מזויף, filename חריג, duplicate ו-R2 failure.
- תאריכים לא חוקיים, תאריכים עתידיים, סכומי קצה ודיוק עשרוני.
- pagination ונתונים מעל מגבלת 50/100/1000.

## סדר תיקון מומלץ

1. לאמת את שכבת הזהות ולחסום spoofing של headers.
2. לבודד IndexedDB לפי משתמש/עסק ולשפר את מודל הסנכרון.
3. להפוך פעולות נתונים ו-audit לאטומיות.
4. לתקן שחזור ו-lifecycle של attachments/R2.
5. להוציא schema setup ממסלול הבקשה ולהריץ migrations בפריסה.
6. להוסיף validation מרכזי לתאריכים, סכומים ו-id-ים.
7. להוסיף בדיקות אינטגרציה ו-browser flows לפני מסירה ללקוח.
8. לאחר מכן לטפל ב-pagination, מטבעות, CSP ו-polish של UX.

## מסקנה

המערכת נראית כמו MVP מתקדם עם בסיס טוב, אך אינה “סגורה” עדיין למידע עסקי רגיש בלי טיפול בארבעת הנושאים הראשונים: זהות, בידוד cache, conflicts ואטומיות נתונים. הבדיקות הירוקות הן נקודת פתיחה טובה, לא אישור production מלא.
